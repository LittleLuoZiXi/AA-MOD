# 发布规则

以下规则适用于今后的每个正式版本。

1. 在 mods/recorder 分支保存完整运行、构建和测试源码及对应版本说明。按实际修改完成必要验证，并核对源码与发布产物的对应关系；保留历史基线，不合并到 main，除非用户另有明确指示。
2. 每个版本都必须上传一个由现有保护构建流程生成的安装 EXE，不发布内部未保护的安装器、开发 DLL 或验证 EXE。保护无法承诺不可逆向。
3. 面向用户的安装包名称固定为“内录MOD{version}版本安装包.exe”，例如“内录MOD1.2.4版本安装包.exe”。文件名及 Release 下载入口不添加“加壳”“保护版”等标记。内部构建目录与中间文件名可保留；发布时复制命名，字节和 SHA-256 必须不变。
4. 同时提供 AARecorder-V{version}-Source.zip 和 AARecorder-V{version}-update.zip。前者是完整源码与准确说明，排除大型依赖、运行日志、用户资料及内部交付现场；后者必须是同一已验收构建的完整 install-payload.zip。
5. 先保存完整源码，再创建或更新对应 Release 并上传资产，核对资产大小与摘要；最后提交 updates/recorder/stable.json。不得让生产清单指向不存在、未上传完成或与摘要不一致的资产。
6. 公开说明应准确描述用户可见功能和实际验证边界。按用户本次明确要求，V1.2.4 的公开发布说明只介绍功能，不叙述本轮内部问题和处理经过。这是仅本次的例外，不自动延续到后续版本；今后的说明按实际变化和当次用户要求编写，不默认省略问题修正。
7. 当前 V1.2.4 发布按用户授权覆盖既有 V1.2.4 源码基线和发行，并移除临时 V1.2.5 测试发布；不因此修改所有历史版本或开发源文件。以后若没有另行指示，仍采用独立版本基线。

发布者应保存本地与远端的版本、源文件索引、提交号、Release 地址及资产摘要记录。不要把旧交付状态、模拟更新版本或内部测试载荷当作当前生产信息。
